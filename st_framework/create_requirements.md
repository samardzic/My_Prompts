# Product Requirements Document (PRD) creation



## Generic version

```text
DOCC = 

Analyze the DOCC file thoroughly and extract all relevant information, including functional requirements, system behavior,
constraints, interfaces, workflows, and any other requirements or specifications contained within it.

Use the DOCC file as the source of truth. Do not invent requirements or introduce assumptions that are not explicitly supported by the source material.

Organize the resulting Requirements Document into a clear, structured, and professional format. Ensure that:

- Requirements are clearly defined, unambiguous, and individually identifiable.
- Requirements are written in a consistent, testable, and verifiable manner.
- Related requirements are grouped into logical sections.
- Functional and non-functional requirements are distinguished where applicable.
- Dependencies, constraints, conditions, and expected behaviors are captured.
- Ambiguities, inconsistencies, missing information, and implicit assumptions in the source are identified and documented separately.
- Traceability to the original DOCC source is maintained wherever possible, including references to relevant sections, paragraphs, tables, or other source locations.

The output should be suitable for use as a formal requirements specification document and serve as a foundation for subsequent development,
review, and test-case creation.

**Do not omit relevant information from the DOCC file. If the source contains insufficient information to define a requirement precisely,
document the gap rather than making assumptions.**
```
